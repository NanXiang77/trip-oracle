# 周末去哪 · 周边拥挤度预测（trip-oracle）

面向**大学生短途出行**的决策助手原型：从长春出发，预测周边 6 个目的地未来 8 天"挤不挤、花多少、值不值"。

先在本机跑通，再把工具层搬到华为云 AgentArts 上。

---

## 一、它解决什么问题

大学生做周末/小长假决策时的真实困境不是"没地方去"，而是：

1. **不知道会挤成什么样**——官方热力图只给"此刻"，不给"我要去的那天"；
2. **不知道要花多少**——车票、住宿、门票分散在多个 App；
3. **不知道哪个更值**——人多的地方可能刚好最便宜，需要一个综合判断。

因此本项目的输出是三件事：**拥挤度日历** + **花费估算** + **排名与理由**。

> 边界：不做"实时人流"（那需要手机信令/闸机数据，拿不到也不该拿），只做**基于公开信号的预测**。

---

## 二、数据从哪来（全部公开、免密钥、低频访问）

| 数据 | 来源 | 频率 | 说明 |
|------|------|------|------|
| 余票 | 12306 公开余票查询页 | 每日 1 次 | 核心信号：余票 = 供给 − 需求 |
| 天气 | Open-Meteo | 每日 1 次 | 7~8 天预报，短途出行的强外生变量 |
| 车站码表 | 12306 `station_name.js` | 7 天缓存 | 中文站名 → 电报码 |

**合规**：只请求公开页面，不登录、不涉及账号与个人信息，单日请求量 < 100 次。

---

## 三、指标体系

```
售罄率     = 售罄车次数 / 有效车次数
座位宽松度 = min(1, 可售座位总数 / (有效车次 × 120))
拥挤指数   = 0.7 × 售罄率 + 0.3 × (1 − 座位宽松度)      # 0 最宽松，1 最挤
等级       = 按 0.15 / 0.30 / 0.50 / 0.70 切成 1~5 档
```

**为什么不用绝对余票数**：不同目的地车次数差异极大（吉林 70+ 趟、长白山 10 趟），绝对张数不可比，必须归一化。

## 五、怎么运行

```bash
python collect.py            # 采集全部目的地（约 2 分钟）
python collect.py 沈阳 延吉   # 只采指定目的地
```

**每日定时采集**（关键，见下一节）：把 `collect.py` 挂到 Windows 计划任务，每天 8:00 与 20:00 各跑一次。

## 更新 2026-11-02：抖音指数层 + 标定/预测/回测分离协议

**抖音指数**：`collectors/douyin.py`——抖音指数已迁至 creator.douyin.com（老 trendinsight 接口废弃），
强制登录。方案：CDP 驱动 Edge（调试端口 9333，专用 profile `data/edge_cdp_profile`）在页面上下文

登录态 HttpOnly，须用 CDP `Network.getAllCookies` 检测；profile 不可并发两个 Edge 实例。

**标定/预测/回测三分离协议（防数据泄漏）**：

热度→客流的换算系数 α **绝不能用预测目标的同期真值标定**（拿答案训练）。数据分三层：

| 层 | 数据 | 用途 |
|----|------|------|
| 标定集 | 预测目标**之前**的日常数据（如长白山 9 月官方 50.12 万 ↔ 抖音 9 月热度） | 拟合"热度→客流"基线换算 |
| 预测集 | 元旦（12/17 放票 + 节前热度） | α 只取自回测得到的先验，不看当期任何数据 |
| 回测集 | 国庆 10/1~10/7 官方真值（venue_daily 表） | 仅事后检验 α 泛化误差，不参与预测计算 |

- 当前约束：只有一个假期的真值，国庆 α 目前只能做事后检验（in-sample）；首个干净的
  跨事件预测实验是**元旦**——用国庆回测出的类型化先验（本地周边型 α≈1.1，
  远程季节型 α≈1.8~2.1 或"出发前 5 天热度积分"变量）预测元旦，误差即为泛化能力。
- 已入库真值（venue_daily）：故宫 10/1=2.94万、10/2=6.26万；中街 10/2=80万；
  长白山 9 月日均 1.67万 + 10/3~5 满额 4.1万/日；中央大街国庆日均 15.3万；延边州日均 87.5万。
- 注意：假期客流几乎全是游客，日常客流混有本地市民，日常期标定的 α 对假期会有
  结构性偏差——跨假期标定（用上一个假期标、预测下一个假期）才是主路径。

### 9/30 视角伪预测回测（只用 9/30 前可得数据）

预测规则（无历史假期标定，先验 α∈[1.0,1.5] 明示为未检验假设）：
客流倍数区间 = [节前6天热度均值倍数, 先行峰倍数 × α_hi]；等级判定阈值 1.3。
回测结果：长白山真实2.45×(预测1.9~2.8✅)、延吉≈3.0×(预测2.1~3.1✅)、
故宫7日均2.56×(预测2.1~3.2,下沿命中,峰值低估)、哈尔滨真实≤1×(预测1.6~2.3❌高估)。
哈尔滨误报根因=季节错配（主场是冰雪季），修正方向：加"目的地旺季月份"特征，
节前信号×季节权重。教训：热度领先信号预测**等级/排序**可靠（4/4方向正确），
预测**数值**需先经一次假期真值标定 α。

## 更新 2026-11-03：前向观测与预警（watch.py）——元旦的正确主力信号

### 为什么不再用热度预测元旦

用三年元旦的百度指数实测（12/31~1/2 窗口，对比前 23 天基线）：

| 元旦 | 长白山 假期倍数 | 沈阳 假期倍数 | 长白山 节前7天倍数 |
|---|---|---|---|
| 2024 | 0.72 | 1.03 | 1.30 |
| 2025 | 0.73 | 1.40 | 0.88 |
| 2026 | 0.97 | 0.98 | 1.07 |

同一假期三年，倍数在 0.72~1.40 之间无稳定方向 —— 这不是"信号弱"，是**没有信号**。
国庆那套 `节前热度 × α` 搬到元旦只会输出一个 ±40% 噪声的数，不如不预测。
（根因：元旦只有 3 天，出行决策周期短，搜索行为没有形成国庆那样的提前量。）

### 换成余票口径：真实预测场景里它才是现成的

回放面板（`replay_matrix`）之所以存在，是因为 **12306 不提供历史余票**。
但真正预测未来时：余票**提前 14 天预售**（实测 2026-11-03：今天 +14 天可查，+15 天返回空）。
即 12/17 开售 12/31 的票，从那天起元旦当天的供给压力**直接可见**，不需要任何反演。

于是新增 `trip_oracle/watch.py`，盯三件事：

1. **售罄时点**（核心）：同样卖完，开售 2 小时售罄和开售 5 天售罄，需求强度差一个量级。
   这个信息只能靠高频快照累积，**事后无法补采**，所以必须提前跑。
2. **去/回双向**：`direction='return'` 一起看，避免"去得了回不来"。
3. **采集管道自身的健康**：连续失败要报警，否则会静默地"看起来一切正常"。

### 表结构（store.py 自动建表）

| 表 | 作用 |
|---|---|
| `soldout_event` | 车次级：`first_seen_at` / `soldout_at` / `hours_to_sold` / `status` |
| `watch_run` | 每轮采集：查询数、写入行数、成功与否、错误信息 |
| `alert_log` | 预警：等级、规则、去重键 `(rule, dest, travel_date)` |

### 指标与预警阈值

指标（`watch.metrics`）：售罄率、**开售后 24h 内最高售罄率**、售罄趟数、最短/中位售罄耗时、
首见即售罄趟数（耗时不可知，单独计数，不混进 0 小时）。

| 规则 | 条件 | 含义 |
|---|---|---|
| A1 | 开售后 24h 售罄率 ≥ 30% | 需求偏强（不用"首轮观测"，那必然为 0） |
| A2 | 某车次 0 < 耗时 ≤ 2h | 极速售罄，极端需求 |
| A3 | 售罄率较上次观测 +20pp | 热度正在涌来 |
| A4 | 连续 3 轮采集失败 | 管道中断（比漏报更危险的是静默失败） |

### 用法与调度

```bash
python -m trip_oracle.watch --status                  # 进度 + 指标 + 预警
python -m trip_oracle.watch --once                    # 采一轮（计划任务调这个）
python -m trip_oracle.watch --loop --interval 60      # 常驻
python -m trip_oracle.watch --once --dry-run          # 只查不落库
python -m tests.test_watch_alerts                     # 规则自检（合成数据，含 A1~A4）
```

计划任务（**12/16 起到 1/3**，期间余票窗口才覆盖元旦）：

```bat
:: 常规每 2 小时一轮
schtasks /create /tn "trip-oracle-watch" /tr "C:/.../trip-oracle/run_watch.bat --once" /sc minute /mo 120
:: 开售日（12/17-12/19）建议加密到 30 分钟，售罄耗时的分辨率就是采集间隔
```

`--status` 在开售前会明确输出"当前没有已开售的目标日期——此刻任何'元旦会有多挤'的数字都是编的"，
这是刻意的：宁可显示"没有信号"，也不给一个看起来精确的假数字。
